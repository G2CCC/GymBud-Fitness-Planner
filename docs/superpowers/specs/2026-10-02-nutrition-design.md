# GymBud 饮食与训练热量功能设计
版本：v1.0 审阅稿  
日期：2026-10-02（Pacific/Auckland）  
项目：https://github.com/G2CCC/GymBud-Fitness-Planner  
状态：产品范围已逐项确认；本文件的默认算法参数与工程细节待整体审阅。尚未修改业务代码、数据库或远程分支。

## 1. 目标与最新决策

为 GymBud 增加固定营养目标、四餐饮食记录、训练消耗估算及每周营养复盘。用户不需要填写额外的日常活动等级，不需要在力量打卡时填写实际时长。

以下为用户已确认的产品要求：

| 项目 | 决策 |
| --- | --- |
| 第一版范围 | 营养目标与记录，不自动安排食谱 |
| 身体目标 | 减脂、增肌、维持，三个单选目标 |
| 热量口径 | 净摄入 = 饮食摄入 − 已完成训练的估算消耗 |
| 目标变化 | 净热量目标和三大营养素目标均固定，不随当天训练变化 |
| 目标来源 | 后端公式计算，不由 AI 生成，不提供手动覆盖 |
| 用户资料 | Sex 仅 MALE/FEMALE；移除另外两个 Gender 选项 |
| 旧数据 | 当前没有用户，不做旧资料兼容、补全或历史回填流程 |
| 年龄 | 不增加年龄门槛，不建立分年龄算法；统一公式仍使用年龄输入 |
| 日常活动 | 不新增资料字段；使用统一默认假设 |
| 力量消耗 | 按实际组数和次数估算各动作时间与热量，再累加；不新增实际时长输入 |
| 有氧和运动消耗 | 继续使用实际时长，系统自动估算，不手动覆盖热量 |
| 食物 | 英文常见食材与基础食品系统库，不加入私人自定义食物 |
| 食物单位 | g 为基础；来源具备可靠单个重量时支持 ea |
| 餐次 | Breakfast / Lunch / Dinner / Snack |
| 记录完整性 | 用户确认当天记录完成；只用完整记录日评价全天摄入 |
| 目标重算 | 资料修改当天起重算，过去日期保持原目标 |
| 每周复盘 | 加入营养统计，与上一周期浅比较；AI 不修改固定目标 |

年龄保留为同一公式的输入，是本轮已说明并采用的解释。“统一公式”不等于忽略年龄变量。成人估算方法在现有全部年龄、身体状况上的有效性不能据此得到保证。产品应明确显示估算属性，不能将这些通用值表述为未成年人或特殊医疗情形的个体饮食处方。

不在本版范围：品牌食品、条码扫描、拍照识别、食谱生成、饮水、微量营养素、设备同步、用户自定义食物、年龄算法分支和兼容旧用户数据的迁移逻辑。

## 3. 用户界面

导航：Calendar / Nutrition / Progress / Profile；移动端导航同步改为四项。

Nutrition 页面：
1. 普通页面标题和日期切换，默认今天。
2. 净摄入进度；同时显示 Food、Exercise、Net 和目标差额。
3. Protein / Carbs / Fat 三项固定目标与实际摄入。
4. 四个餐次列表和 Add food 按钮。
5. 当日已完成训练的估算消耗摘要，链接回现有训练详情。
6. Mark day complete / 已完成状态。

添加食物流程：
搜索英文名称 → 选择具体生熟条目 → 输入重量或数量 → 预览营养 → 保存到餐次。
ea 显示规格和换算，例如“1 large ≈ 来源重量 g”；不把 serving、cup、slice 无差别翻译成“一个”。

操作支持：编辑、删除、过去日期补录。实际饮食记录不允许登记未来日期；不在本版增加未来餐单功能。初次进入且无记录时显示“未记录”，不宣称零摄入。

已完成日再次增删改食物后，自动取消完整确认。目标改变或训练日志变化只更新计算，不取消饮食完整确认，因为该确认仅表示饮食已录全。

视觉沿用现有配色，普通标题、列表和适量分隔线；避免渐变、大标题外包卡片和层层卡片。

## 4. 食物数据来源与导入

### 4.1 建议选择

推荐 USDA FoodData Central 的 SR Legacy 下载数据作为第一版固定数据快照；GitHub 的 alyssaq/usda-sqlite 用于了解现成 USDA 数据组织方式。该仓库附带较旧的 SR28，不把它误称为最新食物数据。

不复制尚未核实许可的第三方导入脚本。USDA 数据本身有明确公共领域/CC0 声明，编写本项目的轻量导入转换器。这样保持用户“采用现成食物库”的目标，同时保留明确的数据来源。

选定数据发布版本与文件校验和，导入结果保存 provider/sourceId/release。SR Legacy 是历史最终版，不宣称会持续更新。后续扩展 Foundation Foods 是独立的数据维护工作。

### 4.2 清理规则

- 热量统一 kcal/100 g，蛋白质、碳水和脂肪统一 g/100 g，可食部分基准。
- 四项数据必须明确存在且为非负有限数；缺失不是零，缺任一核心项不启用。
- 能量按 nutrient ID 与单位选择来源值；不按名称模糊匹配，也不使用“数组第一项”。
- 同时存在 kJ/kcal 时取 kcal；只有 kJ 且来源含义明确时用 4.184 换算。
- 保留生熟、是否加油、去皮与其他影响营养的描述，不将不同处理状态合并。
- 初版启用基础食材与食品，排除品牌/餐厅条目、婴幼儿配方、补充剂等不属于范围的记录。
- 建立可审阅的筛选清单，不编造导入条数；产出导入总数、启用数、排除原因和缺失字段报告。
- ea 仅对明确完整单个可食份量启用；份量为 N 个、重量为 W g 时，单个重量为 W/N。
- 没有可靠 ea 换算就仅支持 g。液体本版也按 g，不默认 1 ml = 1 g。
- 食物热量采用来源数据，不强制替换为蛋白质×4＋碳水×4＋脂肪×9。
- 来源唯一键防重复；导入可重复执行；下架条目停用，不删除已引用食物。

最低人工抽样覆盖：生米、熟米饭、生/熟鸡肉、鸡蛋、牛奶、燕麦、苹果、香蕉、食用油。验证 raw/cooked、ea、缺失数据、单位换算与重跑导入。

## 5. 固定营养目标：本次建议默认参数

本节数值是待审阅的产品默认配置。参考公式有文献依据，但日常活动系数、减脂/增肌调整和具体分配值不是针对每位用户验证过的医学结论。

### 5.1 净热量目标

采用一套 Mifflin–St Jeor 静息能量估算公式：
R = 10 × weightKg + 6.25 × heightCm − 5 × age + S
MALE 的 S = 5；FEMALE 的 S = −161。

默认日常活动假设：baseline = R × 1.2。
不将 weeklyTrainingDays 或计划训练消耗加入 baseline，因为已完成训练会在净摄入中单独扣减。

建议目标系数：
- FAT_LOSS：baseline × 0.90。
- MUSCLE_GAIN：baseline × 1.05。
- MAINTENANCE：baseline × 1.00。

目标 kcal 四舍五入到整数；记录算法版本 nutrition-v1。这里的 1.2、0.90、1.05 是可调整的产品假设，不宣称为各年龄或体型统一有效的临床处方，也不保证按该数值执行就产生特定体重变化。

### 5.2 固定三大营养素

建议：
- FAT_LOSS / MUSCLE_GAIN：proteinG = 1.8 × weightKg。
- MAINTENANCE：proteinG = 1.6 × weightKg。
- fatG = targetKcal × 0.30 / 9。
- carbsG = (targetKcal − 4 × proteinG − 9 × fatG) / 4。

内部计算保留精度，目标存至 0.1 g，显示整数克；不把界面四舍五入后的数再回算热量。实际食物营养使用来源值，而非上述分配公式。

拒绝非有限值、非正热量和负碳水等数学上不成立的组合，返回可解释的 INVALID_TARGET，不静默写入负数或编造替代值。数学校验不代表已经完成营养适用性验证。

以上蛋白质数量级参考健康运动成年人常见的研究范围；精确系数及脂肪比例仍属于产品建议。固定三大营养素与净摄入口径可能不会同时达到 100%，界面不强制其同时达标。

### 5.3 可复现算例

虚构成人输入：MALE，27 岁，180 cm，80 kg。R = 1795，baseline = 2154。

| 目标 | 净 kcal | 蛋白质 g | 脂肪 g | 碳水 g |
| --- | ---: | ---: | ---: | ---: |
| 减脂 | 1939 | 144.0 | 64.6 | 195.3 |
| 增肌 | 2262 | 144.0 | 75.4 | 251.9 |
| 维持 | 2154 | 128.0 | 71.8 | 249.0 |

该算例仅验证运算与显示口径，不是给特定人的饮食建议。

### 5.4 生效与历史

首次完整保存资料生成目标。影响计算的字段变化才重算；仅修改计划训练天数或训练时长不改变目标。
- 当天启用新目标，已有食物记录不变。
- 同一天多次修改，保留当日最新版本作为有效目标；过去日期不变。
- 通过按 effectiveDate 查询目标版本重建每日目标，不要求每天写一条相同记录。
- 修改资料和保存新目标在短事务中完成，避免资料已变、目标未变。
- 不重写历史饮食营养和过去训练消耗。

## 6. 力量训练消耗：不增加实际时长字段

### 6.1 已确认的计算路径

实际组数、次数 → 各动作内部估算时间 → 各动作估算消耗 → 训练总消耗。
只读取实际日志，不从计划组数假装用户全部完成。实际重量继续用于训练量/重量建议，不直接当作热量乘数。

### 6.2 本次建议默认参数

为避免维护八百个未经验证的“单动作热量”，第一版统一使用普通多动作阻力训练参考 MET = 3.5（Compendium code 02054）。每个动作热量不同来自实际完成量与估算时间，不靠人为赋予每个动作固定 kcal。

内部时间启发式：
- repSeconds = 4。
- restSeconds 取已存在的该动作计划值；缺省为 60，明确设置 0 时保留 0。
- 仅 actualReps > 0 的组算有效组。
- R 为该动作实际总次数，S 为有效组数。
- estimatedSeconds = R × 4 + max(S − 1, 0) × restSeconds。
- 不额外添加动作间换场、热身、器械等待和整场计划时长。

动作的额外训练消耗：
estimatedKcal = max(0, MET − 1) × bodyWeightKg × estimatedSeconds / 3600。

减去 1 MET 表示粗略扣除该时段静息部分，减少与日常基准重复记账；它不能彻底消除静息基准、日常活动和个体差异带来的误差。

示例：80 kg，3 组×10 次，组间 60 秒：
estimatedSeconds = 30×4 + 2×60 = 240 秒；
estimatedKcal = 2.5×80×240/3600 ≈ 13.3 kcal。

训练总消耗 = 各动作未取整的结果之和，最后统一保存/展示精度，不先将每个动作取整再求和。所有组为 0 次时该动作贡献为 0，不能通过空日志生成消耗。

MET 参考值有来源，但“每次 4 秒、默认休息 60 秒、动作拆分”的组合是本产品未验证的启发式，不是 Compendium 提供的单动作实测模型。不能声称准确测量热量。不因负重增加自动线性放大消耗。

### 6.3 局限与处理

静态保持动作的“次数”不能反映保持时间；当前只记录次数/重量的模型无法可靠覆盖这类消耗。导入动作元数据时标记重复次数不适用的动作，不为它伪造消耗，显示“未估算”；训练和当日汇总带估算覆盖状态。有缺口的日期可展示已估算小计，但不声称完整净摄入达标。

不新增静态保持计时流程，也不擅自移除现有动作。这是当前简化的明确适用边界。更高精度的计时、强度、设备支持作为后续独立改进。

存储算法版本 strength-energy-v1 和每动作计算输入，便于解释与以后调整。算法更新只影响新计算，不全量改写过去。

## 7. 有氧、运动和完成训练的统一规则

CARDIO/SPORT 保留现有 actualDurationMinutes，默认可由前端带入计划时长，由用户确认实际值。

现有 ActivityOption.id 对应版本化 MET 映射。每个启用的活动都必须有可追溯的映射或明确“不支持估算”状态。默认档位来自具体活动参考条目；速度/强度只在存在明确来源映射时影响选档，不能随意乘强度系数。

采用与力量一致的额外消耗口径：
estimatedKcal = max(0, MET − 1) × bodyWeightKg × actualDurationMinutes / 60。
不同时使用 1 kcal/kg/h 和 3.5 ml/kg/min 换算造成版本混杂。

完成/补登记接口：
- STRENGTH 必须存在合法的实际动作日志，无实际时长输入。
- CARDIO/SPORT 必须存在实际时长。
- 可以提交新日志，也可以使用已保存且校验通过的日志；无日志时返回 VALIDATION_ERROR。
- 状态变更、完成时间、日志和消耗快照在同一短事务提交。
- 只有 COMPLETED 才进入当天消耗；PLANNED 日志草稿不产生抵扣。
- 编辑未锁定训练日志时替换原消耗快照，不能追加第二份消耗。
- 保留现有已关闭周期的训练修改限制，不为本功能放开已完成训练删除。
- 补登记按 completedAt 在记录时区对应的实际日期归属，不按 scheduledDate 或提交时间。
- 本次创建日期前没有体重历史时，使用当前可用体重并记录 bodyWeightSource=PROFILE_AT_LOGGING，不伪称当日实测体重。
- 更新当前体重不自动重算已存消耗；修正同一日志默认沿用其身体参数快照。

## 8. 每日汇总、时间和完整性

Food intake = Σ FoodLog 的热量。
Exercise expenditure = Σ 当地日期属于当天的已完成训练估算。
Net intake = Food intake − Exercise expenditure。
Remaining = target − Net intake。

净摄入可为负，服务端不裁剪成零；界面进度条可在 0–100% 范围绘制，但文本显示真实值。超过目标显示超出数量，不显示负的“还可摄入”。它不等于人体全天热量盈余/缺口。

所有餐次与食物营养由日志快照汇总。无日志且未确认完整应显示“未记录”，不能直接用于全天评价。

NutritionDay 以 userId + localDate 唯一。日期使用 PostgreSQL DATE 或严格 YYYY-MM-DD；前端日期选择不经过 new Date('YYYY-MM-DD') 的隐式时区转换。时间戳统一存 UTC，另存归属时区和本地日期。

初次进入从设备读取 IANA 时区并保存为用户记录时区；后端用保存的时区判定“今天”。设备更换时区后，新日期可以采用新时区，但已经存在的日记录和训练归属不自动移动。同一本地日期最多一条日记录，其时区固定。周期复盘使用周期既定起止本地日期筛选，不因显示日历为 Mon–Sun 而改变周期窗口。

允许从开始使用营养功能之日起补录过去日期；首次目标版本之前不回填假目标。确认空白日会产生“用户确认记录完整、但为零”的事实，界面提示是否漏记，AI 不赞扬低摄入。没有完整日时返回空值/无有效样本，不除以零。

## 9. 数据结构

以下为设计字段，不是已经修改的 Prisma schema。

| 模型 | 核心字段与约束 |
| --- | --- |
| UserProfile | sex: Sex 必填；primaryGoal: BodyGoal 必填；保留 age/heightCm/weightKg；增加记录时区 |
| Food | name、sourceProvider、sourceId、sourceRelease、kcal/protein/carbs/fatPer100g、active；来源复合唯一键 |
| FoodPortion | foodId、label、quantity、grams；仅向用户暴露可验证的 ea 单位 |
| NutritionTarget | userId、effectiveDate、四项目标、profileSnapshot、algorithmVersion；用户/生效日期索引 |
| NutritionDay | userId、localDate、timezone、completedAt、revision；用户/日期唯一 |
| FoodLog | dayId、mealType、foodId、portionId?、quantity、unit、grams、nameSnapshot、四项营养快照、clientRequestId |
| WorkoutLog 扩展 | estimatedCaloriesKcal?、energyMethod、energyVersion、energyInputs JSON、energyCoverage、completedLocalDate、timezone |
| CycleReviewSnapshot 扩展 | nutritionSummary JSON，保留原训练 objectiveSummary 结构，避免破坏旧训练量读取 |

不为力量日志增加 actualDurationMinutes；内部 estimatedSeconds 只放计算快照，并标明 estimated。

金额式小数精度用于份量和营养数值（例如 Prisma Decimal），API 显式序列化为有限数字；不依赖数据库小数直接 JSON 化的隐式行为。前端显示取整不影响源数据。

FoodLog 保存食物和营养快照，食物库更新不改旧餐。停用食物不能新增记录，原记录仍可查看和调整已保存份量；重新选择另一食物时生成新快照。

| GET /api/nutrition/day?date= | 目标、四餐、三大营养素、训练和覆盖状态 |
| POST /api/nutrition/entries | 添加食物；提交食物 ID、份量、单位、日期和餐次 |
| PATCH /api/nutrition/entries/:id | 编辑份量、餐次或食物，重新计算并取消完整确认 |
| DELETE /api/nutrition/entries/:id | 删除记录并取消完整确认 |
| PUT /api/nutrition/days/:date/completion | 设置/取消完整确认，带 revision 防并发覆盖 |
| 现有 Profile 保存 | 同一事务更新资料和生效目标 |
| 现有 workout 完成/补登记/日志保存 | 统一日志校验与消耗写入 |
| 现有 weekly review | 增加营养摘要输入和输出 |

用户 ID 取认证上下文，不能信任 body.userId。foodId/portionId 必须匹配、可用且单位合法。热量和营养值不接受客户端权威值。

写入使用 clientRequestId 等唯一键实现网络重试幂等。修改不同餐或并发确认时检查日 revision；返回 409 后前端刷新。不要把食物目录下载、AI 请求放进数据库事务。

错误包括：400 非法份量/日期/单位/目标；404 无权访问或不存在的记录；409 数据版本冲突。错误信息可用于界面显示，不暴露数据库信息。

## 11. 每周复盘

沿用现有周期实际 startDate–endDate，不新增第二套饮食周期，也不因为用户延迟关闭周期而把结束日后的饮食收入旧周。

服务端先生成确定性 nutritionSummary，AI 负责解释：
- 周期总天数、饮食完整天数、具有目标的有效天数。
- 完整日期的平均热量摄入、三大营养素和逐日目标差距。
- 有完整训练消耗估算的日期才用于净摄入目标对比；其他日期单独报告覆盖缺口。
- 每个日期使用当时的目标；平均差距以逐日差距平均计算。
- 上一周期样本数与同口径平均值；不拿 2 天总量和 7 天总量直接比较。
- 无完整记录时输出“饮食记录不足”，不视为零摄入，不阻止训练复盘。
- 默认少于 3 个完整日只做记录描述，不下整周饮食趋势结论；此阈值是产品假设。
- 不凭热量记录声称实际增肌、减脂或体重变化；缺少体重趋势就明确无法判断。
- 不要求四项进度同时达到 100%；不因营养素超参考值就一律判定失败。
- AI 不修改营养目标，也不生成食谱；下周期训练流程沿用现有规则。

复盘读取并保存一个一致的营养快照后再调用 AI。生成期间的饮食更新不混入已经生成的文本。后续补录不重写已保存报告，报告注明“截至生成时记录”。营养功能在无训练周期时仍可使用，但本版不另加纯饮食周期生成器。

## 12. 数据变更与交付

没有真实用户，因此：
- 删除四选 Gender 类型，改为两选 Sex；不保留旧值转换/待补全状态。
- primaryGoal 收紧为三个枚举。
- 不做历史营养目标回填和旧训练消耗补算。
- 测试数据使用新结构生成。
- 新 migration 保证空数据库从现有迁移链能建立最终结构；不随意删改无关迁移。
- 本文不执行数据库清空。后续开发仅对明确的开发/测试数据库按新结构重建，数据库执行与代码提交是两个独立操作。

工程分层：
- shared：目标公式、力量消耗估算、单位换算、营养汇总、校验和接口类型。
- server/src/nutrition：目录查询、日志、每日目标与复盘数据加载。
- server/src/workouts/service.ts：完成与补登记的原子保存。
- server/src/reviews/service.ts、AI prompt/schema：营养摘要接入。
- client/src/pages/nutrition：日记页面与食物选择。
- ProfileForm、API contracts、导航、seed、fixtures：同步 Sex/BodyGoal 和目标状态。
- prisma 与数据脚本：模型、迁移、食物导入、来源清单和授权说明。

## 13. 分阶段开发顺序与验收

| 阶段 | 交付 | 主要验收 |
| --- | --- | --- |
| 1. 资料与计算 | Sex/BodyGoal、新模型、目标计算、力量估算纯函数 | 公式样例一致，年龄只作为输入，力量无时长输入 |
| 2. 系统食物库 | 固定版本数据、清理报告、导入、搜索 API | 生熟正确，ea 可追溯，缺失不变零，重跑不重复 |
| 3. 饮食日记 | 四餐 CRUD、目标、完整确认和日期切换 | 编辑后准确汇总，防重复提交，跨用户不可访问 |
| 4. 训练接入 | 力量按动作累计，有氧运动按时长，补登记 | 不漏日志、不重复抵扣、归属实际完成日 |
| 5. 周复盘 | 确定性营养摘要、AI 解释、上周比较 | 只用有效样本，缺失不当零，不自动改目标 |
| 6. 回归与文档 | 迁移演练、端到端流程、README/数据来源 | 原训练流程通过，移动端四项导航可用 |

关键测试：
1. g 与 ea 产生相同等价重量时营养相同；小数份量和来源单位转换正确。
2. 同一食物库更新不改旧餐快照；用户修改份量按旧快照基准重算。
3. 目标变化只影响当天及以后，历史日期继续读取原目标。
4. 力量只按实际非零组计算，0 次、缺省休息、显式 0 秒分别正确；不按负重线性放大。
5. 不支持时间推导的静态动作保留覆盖缺口，不伪造全量估算。
6. 完成、补登记、保存日志的不同入口均应用相同校验与算法。
7. 对同一已完成日志修正，只替换一次消耗；PLANNED 不扣热量。
8. Auckland 的午夜与夏令时、补录昨天、日期选择不偏移一天。
9. 两个并发新增都保留；重试只生成一次；确认与编辑冲突可恢复。
10. 周期中途改目标、无记录、部分记录、上一周缺失、延迟关闭均汇总正确。
11. 计算不输出 NaN、Infinity、负宏量目标；错误不产生半条目标。
12. AI 故障不丢饮食记录、不阻断日记；原复盘重试路径仍可用。

仓库级验证沿用现有 shared/server/client typecheck、相关单元与集成测试、client build、Prisma validate 和覆盖该流程的 E2E。数据库集成测试必须在隔离测试环境运行，不将“未运行”报告为通过。
